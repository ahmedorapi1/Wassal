Wasel

منصة توصيل عند الطلب تربط أصحاب المحلات بمندوبي توصيل مستقلين بالموتوسيكلات، بنموذج قريب من تطبيقات النقل عند الطلب، لكن مخصص لتوصيل المنتجات والطلبات من المحل إلى العميل.

اسم المشروع: Wasel السوق الأولي: مصر واجهة عربية RTL + إنجليزية لاحقًا MVP قابل للتوسع Web Admin + Mobile Apps
الهدف الأول: تشغيل أول طلب حقيقي من لحظة إنشائه بواسطة صاحب المحل، مرورًا بقبول المندوب، وحتى التسليم وإثباته، مع حساب تكلفة التوصيل وعمولة المنصة.

1. مبادئ المنتج

ابدأ صغيرًا

تنفيذ رحلة توصيل واحدة بشكل كامل وموثوق قبل بناء الأنظمة المعقدة.

قابلية التوسع

تصميم قاعدة البيانات والخدمات من البداية لدعم الفروع، الشركات، المدن، المركبات، والطلبات المتعددة.

الأمان أولًا

التحقق من الهوية، تتبع الحالات، إثبات الاستلام والتسليم، وسجل تدقيق لكل عملية.

سرعة الاستخدام

صاحب المحل يجب أن يطلب مندوبًا خلال أقل عدد ممكن من الخطوات.

فصل الأنظمة

الخريطة، الدفع، الرسائل، والإشعارات تُبنى خلف واجهات قابلة لاستبدال المزود دون إعادة كتابة المنتج.

قرارات قابلة للتفعيل

تحصيل الكاش، التسعير وقت الذروة، والطلبات المجمعة تُدار عن طريق Feature Flags.

MVP المرحلة التالية توسع مستقبلي قرار منتج مفتوح

2. المستخدمون والأدوار

صاحب المحل

ينشئ طلبات التوصيل، يتابع المندوب، يدفع تكلفة الخدمة، ويشاهد التقارير.

موظف المحل

ينشئ ويتابع الطلبات حسب الصلاحيات، بدون الوصول الكامل إلى الإعدادات والبيانات المالية.

المندوب

يستقبل الطلبات القريبة، يقبلها، يستلمها، يوصلها، ويثبت التسليم.

الإدارة

تراجع الحسابات والمستندات، تراقب الطلبات، تضبط الأسعار، وتحل النزاعات.

RBAC: يجب تطبيق صلاحيات واضحة من البداية: Owner، Manager، Staff، Courier، Support، Operations Admin، Finance Admin، Super Admin.

3. نطاق الـMVP

الـMVP لا يعني تطبيقًا ناقصًا؛ بل رحلة أساسية مكتملة يمكن تشغيلها فعليًا واختبار نموذج العمل بها.

تطبيق صاحب المحل MVP

  • تسجيل حساب وإنشاء متجر.
  • حفظ موقع المتجر.
  • إنشاء طلب فوري.
  • إدخال بيانات العميل والعنوان.
  • تحديد نوع وحجم الطلب.
  • عرض تكلفة التوصيل قبل التأكيد.
  • متابعة حالة الطلب والمندوب.
  • سجل الطلبات والتقييم.

تطبيق المندوب MVP

  • التسجيل ورفع المستندات.
  • قبول أو رفض الطلب.
  • تغيير الحالة إلى متاح/غير متاح.
  • الملاحة لموقع الاستلام والتسليم.
  • تأكيد الوصول والاستلام.
  • إثبات التسليم بـOTP أو صورة.
  • ملخص الأرباح والرحلات.

لوحة الإدارة MVP

  • مراجعة وقبول المندوبين.
  • إدارة أصحاب المحلات.
  • مشاهدة الطلبات الحالية.
  • تعديل التسعير والعمولة.
  • إدارة الطلبات الملغاة والمشكلات.
  • تقارير تشغيلية ومالية أساسية.
خارج الـMVP: الطلبات المجمعة، الاشتراكات، الفروع المتعددة، إخفاء أرقام الهاتف، الذكاء الاصطناعي، الاستيراد من Excel، الـAPI الخارجي، والتسعير الديناميكي الكامل.

7. دورة الطلب الأساسية

إنشاء الطلب: صاحب المحل يدخل بيانات الاستلام والتسليم والأوردر.
التسعير: النظام يحسب المسافة والسعر ويعرضه قبل التأكيد.
البحث عن مندوب: إرسال العرض لأقرب مجموعة مناسبة.
القبول: أول مندوب مؤهل يقبل، ويُغلق العرض على الآخرين.
الوصول للمحل: المندوب يتجه للاستلام ويؤكد الوصول.
استلام الأوردر: تأكيد الاستلام بكود أو تأكيد متبادل.
التوصيل: تتبع حي للمندوب أثناء الرحلة.
إثبات التسليم: OTP أو صورة أو توقيع حسب الإعدادات.
الإغلاق المالي: إضافة أجر المندوب، تسجيل عمولة المنصة، وإصدار إيصال.
التقييم: صاحب المحل يقيّم المندوب، وتُحدّث مؤشرات الجودة.

8. التسعير والعمولة

معادلة MVP

السعر = رسم فتح الطلب + سعر لكل كيلومتر + رسوم حجم/وزن اختيارية + رسوم انتظار.

  • حد أدنى للسعر.
  • تقريب واضح للعملة.
  • تسجيل نسخة التسعير المستخدمة مع كل طلب.
  • دعم أسعار مختلفة حسب المدينة أو المنطقة.

عمولة المنصة

العمولة الأساسية تُحصّل من صاحب المحل، وليس من المندوب، لتسهيل جذب المندوبين في البداية.

  • نسبة مئوية من رسوم التوصيل.
  • أو مبلغ ثابت لكل طلب.
  • أو نظام هجين.
  • إمكانية باقات شهرية بعمولة أقل لاحقًا.
مهم: لا تكتب التسعير داخل الكود بشكل ثابت. أنشئ Pricing Rules في قاعدة البيانات مع تاريخ سريان وVersion.

9. تحصيل قيمة الأوردر كاش

قرار المنتج المفتوح: هل المندوب سيحصّل قيمة الأوردر من العميل ويسلّمها لصاحب المحل، أم دوره توصيل فقط؟

حتى لا يتوقف التنفيذ، يُبنى النظام من البداية لدعم الحالتين، لكن يتم تعطيل تحصيل الكاش افتراضيًا باستخدام Feature Flag.

الوضع الأول: Delivery Only MVP Default

  • المنتج مدفوع مسبقًا أو تتم محاسبته خارج المنصة.
  • المندوب يحصل فقط على رسوم التوصيل.
  • مخاطر مالية أقل وتشغيل أسرع.

الوضع الثاني: Cash on Delivery Decision

  • صاحب المحل يدخل قيمة الأوردر.
  • المندوب يرى قيمة التحصيل قبل القبول.
  • يتم تسجيل مبلغ مستحق على المندوب.
  • تسويات يومية أو دورية مع حدود ائتمانية.
  • منع قبول طلبات جديدة عند تجاوز حد النقد.
متطلبات COD عند تفعيله
  • Courier Cash Ledger لكل مندوب.
  • Store Settlement Ledger لكل متجر.
  • إثبات التحصيل وإثبات التسوية.
  • حد نقدي للمندوب حسب مستوى الثقة.
  • تنبيهات للمديونيات المتأخرة.
  • مسار نزاع واضح في حالة اختلاف المبلغ.
  • عدم تعديل قيمة الأوردر بعد الاستلام إلا بموافقة إدارية وتسجيل Audit Log.

12. المعمارية التقنية المقترحة

المعمارية المقترحة تبدأ كـModular Monolith منظم، وليس Microservices مبكرًا، مع حدود واضحة تسمح بالفصل لاحقًا.

التطبيقات

  • merchant-web أو merchant-mobile: تطبيق صاحب المحل.
  • courier-mobile: تطبيق المندوب.
  • admin-web: لوحة الإدارة.
  • api: الخدمات وقواعد العمل.
  • worker: المهام الخلفية والإشعارات وإعادة المحاولة.

Stack مقترح

  • Frontend Web: Next.js + TypeScript.
  • Mobile: React Native / Expo.
  • Backend: NestJS + TypeScript.
  • Database: PostgreSQL + PostGIS.
  • Cache/Queues: Redis + BullMQ.
  • Realtime: WebSockets / Socket.IO.
  • Storage: S3-compatible object storage.
  • Observability: structured logs + error tracking.

17. معايير قبول الـMVP

سيناريو النجاح

  1. صاحب متجر جديد يسجل وينشئ متجرًا.
  2. ينشئ طلبًا ويحصل على سعر واضح.
  3. مندوب موثق ومتصل يستقبل العرض ويقبله.
  4. تظهر حالة وموقع المندوب لصاحب المحل.
  5. المندوب يؤكد الاستلام.
  6. العميل يستلم ويتم إثبات التسليم.
  7. الطلب يُغلق وتُسجل العمولة والأجر.
  8. يظهر الطلب في التقارير وسجل الأحداث.

الجودة المطلوبة

  • لا يمكن تخطي حالات الطلب بصورة غير قانونية.
  • لا يمكن لمندوبين قبول نفس الطلب.
  • كل عملية مالية تُسجل كـLedger Entry.
  • كل إجراء إداري حساس يظهر في Audit Log.
  • الواجهات تعمل بالعربية وRTL بشكل أصلي.
  • الواجهات متجاوبة مع الموبايل والويب.
  • اختبارات وحدة وتكامل للـworkflow الأساسي.
  • Seed Data وDemo Mode لتجربة المشروع.
  • README واضح لتشغيل المشروع محليًا.

18. برومبت البداية لكوديكس

انسخ النص التالي إلى Codex كبداية للمشروع. يطلب منه تنفيذ الأساس فقط أولًا، مع الحفاظ على قابلية التوسع.

You are building a production-oriented MVP called "Wasel", an on-demand delivery platform for Egypt.

Business model:
- Merchants such as supermarkets, grocery shops, pharmacies, restaurants, and other stores create delivery requests.
- Independent motorcycle couriers receive nearby delivery offers, accept a job, pick up the order from the store, and deliver it to the final customer.
- The platform earns a commission from the merchant.
- Cash-on-delivery must be supported by the architecture but disabled by default behind a feature flag until the product decision is finalized.

Build the project as a scalable modular monolith in a TypeScript monorepo.

Recommended apps:
- apps/api: NestJS backend
- apps/admin-web: Next.js admin dashboard
- apps/merchant-web: Next.js responsive merchant app
- apps/courier-mobile: React Native / Expo courier app
- apps/worker: background jobs

Recommended infrastructure:
- PostgreSQL with PostGIS
- Prisma ORM
- Redis and BullMQ
- WebSockets / Socket.IO for real-time updates
- S3-compatible storage abstraction
- Provider abstractions for maps, OTP/SMS, payments, push notifications, and phone masking

Core MVP modules:
- Authentication with OTP provider abstraction and local mock provider
- Users and RBAC
- Merchants and stores
- Couriers, vehicles, and document verification
- Orders
- Pricing rules and price quotes
- Dispatch offers
- Live order tracking
- Proof of pickup and proof of delivery
- Ratings
- Admin operations
- Audit logs
- Feature flags
- Basic wallet/ledger foundation without enabling COD

Required order state machine:
draft
quoted
searching_courier
courier_assigned
courier_arriving_pickup
at_pickup
picked_up
in_transit
at_dropoff
delivered
delivery_failed
returning_to_store
returned
cancelled

Key rules:
1. Every order state transition must be validated and saved as an immutable OrderEvent.
2. Two couriers must never be able to accept the same order.
3. Order creation and financial operations must support idempotency keys.
4. Pricing must be database-driven and versioned, not hard-coded.
5. All financial activity must use immutable ledger entries.
6. All sensitive admin actions must be written to an audit log.
7. Arabic and true RTL must be first-class, not a literal translation layer.
8. External providers must be implemented behind interfaces/adapters.
9. Use feature flags for COD, surge pricing, scheduled deliveries, multi-stop delivery, and subscriptions.
10. Start with a modular monolith and clear domain boundaries; do not create microservices yet.

MVP user journeys:

Merchant:
- Sign up with phone OTP
- Create and configure a store
- Create a delivery order
- Select pickup and drop-off coordinates
- Add customer data and package details
- Receive a delivery price quote
- Confirm the order
- See courier assignment and live status
- Track the courier
- Cancel according to cancellation rules
- See proof of delivery
- View order history and submit a rating

Courier:
- Sign up and upload identity and vehicle documents
- Wait for admin approval
- Set availability online/offline
- Receive nearby order offers
- See pickup distance, delivery distance, and expected earnings
- Accept or reject an offer
- Navigate to pickup
- Confirm arrival and pickup
- Navigate to drop-off
- Confirm delivery using OTP or photo
- View trip history and earnings summary

Admin:
- Review and approve courier documents
- Manage merchants and couriers
- See active orders on a live map
- Inspect the full event timeline of an order
- Manually assign or intervene with proper audit logging
- Configure pricing rules and platform commission
- Review cancelled, failed, and delayed orders
- View basic operational and financial reports
- Manage feature flags

Implementation sequence:
Phase 0:
- Initialize the monorepo and tooling
- Add Docker Compose for PostgreSQL and Redis
- Add shared TypeScript config, linting, formatting, testing, env validation, localization, and UI foundations
- Create architecture documentation and ADRs
- Create database schema and migrations
- Add seed data and demo users

Phase 1:
- Implement auth, RBAC, merchants, stores, couriers, vehicles, documents, and admin verification
- Add API contracts and tests

Phase 2:
- Implement pricing, order creation, order state machine, order events, and cancellation rules
- Add unit and integration tests

Phase 3:
- Implement dispatch offers with concurrency protection
- Add courier availability and location updates
- Add real-time order updates

Phase 4:
- Implement pickup, transit, delivery proof, ratings, basic ledgers, reports, and audit logs
- Finish the three user interfaces

Do not try to build all phases in one uncontrolled pass.
Start by:
1. Inspecting the repository if it already exists.
2. Creating a detailed implementation plan.
3. Generating the monorepo foundation and architecture documentation.
4. Implementing Phase 0 completely.
5. Running all checks and reporting exactly what was created, what passes, and what remains.

Create a professional README with exact local setup instructions for Windows and Linux.
Never fabricate successful test results. Run the commands and report their real output.
