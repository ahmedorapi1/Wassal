# تقرير اختبار إلغاء الطلب ومهلة قبول المندوب

التاريخ: 2026-08-02  
المشروع: SKKA / سِكّة  
Migration: `20260802120000_order_cancellation_acceptance_timeout`

## النتيجة التنفيذية

تم تشغيل البنية المحلية والخدمات والاختبارات فعليًا، ولم يقتصر التحقق على
مراجعة الكود. منطق الإلغاء ومهلة قبول المندوب يعمل حسب قاعدة العمل المتفق
عليها. نجح التشغيل النهائي الكامل في **59 ملف اختبار و297 اختبارًا من 297**.

تم اكتشاف عيب تشغيل محلي في أوامر Merchant/Admin المنفردة، وثلاث مشكلات عزل
لبيانات الاختبارات. أُصلحت هذه المشكلات وأضيفت/وسعت اختبارات الانحدار. لم يظهر
عيب في قاعدة العمل المالية أو في انتقالات الإلغاء والمهلة نفسها.

## تحقق الواجهات الفعلية

### Merchant Web

تم تسجيل الدخول من الواجهة الفعلية بحساب owner، والتحقق من:

- اتصال التحديث المباشر.
- رسالة انتهاء المحاولة الأولى وزر `إعادة البحث عن مندوب`.
- بدء المحاولة الثانية على نفس رقم الطلب وعدّاد خمس دقائق.
- انتقال Worker الحي إلى الحالة النهائية دون إعادة تحميل الصفحة.
- اختفاء زر إعادة البحث بعد المحاولة الثانية.
- استمرار زر الإلغاء المجاني في حالتي انتهاء البحث.
- ظهور تحذير الإلغاء بعد الاستلام وزر `إلغاء وإرجاع الطلب إلى الفرع`.
- ظهور حالة الإرجاع ضمن سجل الطلبات.

### Admin Web

تم تسجيل الدخول كـsuper admin من الواجهة الفعلية وفتح الطلب المستخدم في الاختبار.
ظهرت البيانات التالية:

- `2 من 2` لمحاولات البحث.
- وقت النشر والانتهاء لكل محاولة.
- أحداث `courier search requested`, `expired`, `restarted`, ثم `expired`.
- قيمة أثر مالي `0` وعدم وجود قيد مالي للـtimeout.
- سجل الأحداث وسجل التدقيق غير القابلين للتعديل.
- حقول سبب الإلغاء، توقيته، المنفذ، قبل/بعد الاستلام، وقيمة الاستحقاق.

### Courier Mobile

نجح Expo Metro ونجح Android Expo export. نجحت اختبارات React Native التي تتحقق
من حذف البطاقات المنتهية محليًا، الرسالة العربية للقبول المتأخر، وتعليمات
المرتجع بعد إلغاء التاجر عقب الاستلام. كما اختبر API الحي أن الطلب المنتهي غير
موجود في السوق وأن قبوله يعيد 409 والرسالة العربية الصحيحة.

لم يوجد Android SDK/`adb` أو جهاز Android متصل في بيئة التنفيذ، لذلك لم يتم
ادعاء تحقق بصري على جهاز Android حقيقي.

## اختبارات التزامن والتكرار

- قبول 10 مناديب: نجاح واحد و9 استجابات 409.
- قبول مقابل انتهاء المهلة: Worker والـHTTP في `Promise.all`؛ انتهى الطلب
  `NO_COURIER_AVAILABLE` ولم ينشأ `COURIER_ACCEPTED` أو ledger.
- إلغاء مقابل قبول: نتيجة ناجحة واحدة و409 واحدة، وحدث domain واحد فقط.
- إلغاء بعد pickup مقابل `in-transit`: فائز واحد، ثم استقرار على
  `RETURNING_TO_STORE` وقيمة التوصيل الأصلية.
- تكرار الإلغاء بنفس idempotency key: استجابة مستقرة وحدث وإشعار واحدان منطقيًا.
- تكرار إعادة البحث: حدث `COURIER_SEARCH_RESTARTED` واحد، ومحاولة ثانية فقط.
- تشغيل Worker مرتين: انتقال واحد وحدث timeout واحد وعدم وجود ledger.

## الأخطاء المكتشفة والإصلاحات

1. **`Failed to fetch` في Merchant/Admin عند التشغيل المنفرد**
   - السبب: `dev:merchant` و`dev:admin` لا يحمّلان `.env`، فاستُخدم fallback على
     API port 3000 بدل 3100.
   - الإصلاح: تمرير `dotenv -e .env --` في scriptين الجذر وإضافة اختبار انحدار.

2. **اختبار service-zone غير حتمي**
   - السبب: اختيار أول متجر نشط، وقد يكون قريبًا بما يكفي فلا يتجاوز route limit.
   - الإصلاح: اختيار الفرع الذي أنشأه الاختبار نفسه.

3. **اختبار Worker يعتمد على حالة demo متغيرة**
   - السبب: سجل النزاع الثابت قد يكون أصبح `COMPLETED` في اختبار سابق.
   - الإصلاح: ترتيب حالة الطلب والنزاع داخل setup، وعدم حذف ledger immutable؛
     بدلًا من ذلك تتم مقارنة العدد قبل/بعد للتأكد من عدم إضافة قيد جديد.

4. **اختبار تسجيل التاجر يتأثر بمحدد Redis المتبقي**
   - السبب: مفتاح `merchant-registration:ip:*` ظل بين التشغيلات، فأعاد 429 قبل
     duplicate conflict المتوقع 409.
   - الإصلاح: تنظيف مفاتيح rate-limit الخاصة بالاختبار قبل وبعد المجموعة.

5. **نقص تغطية سباق القبول/Worker وحالة التوجه للاستلام**
   - الإصلاح: إضافة E2E مباشر للسباق، وإضافة E2E مستقل لحالة
     `COURIER_ARRIVING_PICKUP`.

## ما لم يمكن اختباره فعليًا

الجزء الوحيد غير المنفذ بصريًا هو تشغيل Courier Mobile على جهاز Android حقيقي،
لعدم وجود `adb` أو emulator أو جهاز متصل. لإكمال هذه النقطة فقط:

1. تأكد أن الهاتف والكمبيوتر على الشبكة نفسها وأن `EXPO_PUBLIC_API_URL` يحمل
   عنوان IPv4 الصحيح للكمبيوتر والمنفذ 3100.
2. افتح طرفية تفاعلية وشغّل `pnpm.cmd dev:courier` ثم امسح QR عبر Expo Go.
3. سجل الدخول بالحساب `+201001000013` / `CourierDemo123`.
4. تحقق من اختفاء بطاقة الطلب عند انتهاء المهلة ومن رسالة القبول المتأخر.
5. ألغِ طلبًا معينًا قبل الاستلام وتحقق من الإشعار والاختفاء.
6. ألغِ طلبًا بعد `PICKED_UP` وتحقق من تحوله إلى مسار الإرجاع وقيمة التوصيل
   الأصلية دون رسم مرتجع إضافي.

البصري النهائي على جهاز Android حقيقي.
